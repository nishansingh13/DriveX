How DriveX stores a file, and what that buys you

DriveX never keeps a file in one piece in one place. It cuts the file into 1 MB chunks, stores every chunk twice on different storage nodes, and checks a fingerprint of each chunk whenever it reads it back. The result is a file that survives a dead node and notices when its own data has been damaged.

The journey of one file

This is exactly what happens when you press Upload, in the order it happens.

1. Arrives wholeThe browser sends the file in a single request. Multer saves it to a temporary file.
2. Cut into chunksThe server reads the temp file 1 MB at a time. The last chunk holds whatever is left.
3. FingerprintedEach chunk gets a SHA-256 hash. Think of it as a checksum that changes if even one byte changes.
4. Stored twiceChunk i goes to node (i mod 4)+1 and the next node: always two different nodes.
5. RecordedMongoDB keeps the map: each chunk's number, size, hash and its two nodes. The temp file is deleted.

Files live as plain .chunk files in server/storage/node1…node4. Everything about the files (who owns them, what the chunks are, where they live) lives in MongoDB. The data and the map are deliberately kept apart.

    Three things to try

    1. One node dies. Store a file, press Take offline on node2, then Download. The file still arrives; every chunk with a copy on node2 is read from its other copy.
    2. Data quietly goes bad. Press Damage a random copy a few times, then Download. The hash does not match, DriveX reads the other copy and rewrites the bad one. Download again: clean.
    3. Two nodes die. Take node2 and node3 offline together, then download: it is refused up front with a clear error instead of sending a broken file. Now try node1 and node3 instead.

    What if two nodes fail at once?

    It depends which two. Chunk copies always sit on neighbouring nodes (1+2, 2+3, 3+4, 4+1), so a pair of neighbours shares a quarter of the chunks, while opposite nodes share none. Table for a file of 6 chunks (change the slider above):

    This is the limit the report states in §4.1.3: with two copies, DriveX is designed to survive one node failure at a time. Opposite pairs surviving is a bonus of the placement rule, not a guarantee to rely on.

    What it does not do

    Honest limits

    • The four "nodes" are folders on one machine. If the disk or the computer dies, everything goes. This shows how distributed storage works; it is not real disaster protection.
    • Two copies cost 2× the disk space. That is the price of surviving a failure.
    • An upload is one request, so a dropped connection means starting over. Chunking happens on the server.
    • If both copies of one chunk are damaged, that file cannot be recovered. Repair needs one good copy to copy from.

    Why it is still worth showing

    • It is the same idea as Google File System and HDFS (fixed-size blocks, several replicas, checksums), at a size you can see.
    • Every behaviour can be demonstrated live: kill a node, corrupt a byte, watch it recover.
    • Security sits on top: bcrypt passwords, JWT sessions, and every file query filtered by owner.
